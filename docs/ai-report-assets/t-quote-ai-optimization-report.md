# T 型报价优化：AI 辅助工程提效分析报告

## 1. 汇报定位

本次 T 型报价优化的汇报重点不是单点功能修改，而是展示开发人员如何将 AI 纳入工程研发流程，围绕高频行情组件完成问题分析、技术路线选择、跨文件改造、验证闭环和知识沉淀。

本报告建议配合 `docs/ai-report-assets/` 下的 6 张图片使用，可直接拆分为 PPT 内容。

## 2. 背景与问题

T 型报价表属于高频行情和复杂交互叠加场景，主要特点包括：

- 行情刷新频率高。
- 表格行列数量多。
- 横向、纵向滚动同时存在。
- 最新价线、排序、展开收起、点击跳转、主题适配等能力集中在同一组件。

原实现基于 ArkUI 多组件表格，每个 cell 都是独立组件。高频行情刷新时，会触发大量组件更新和响应式传播，导致 UI 线程压力明显。早期通过降低刷新频率或合并调度可以缓解问题，但无法彻底解决 per-cell 组件结构带来的长帧风险。

## 3. AI 提效方式

本次 AI 的使用方式不是简单生成代码，而是作为工程协作工具进入完整研发链路。开发人员负责判断、取舍和验证，AI 辅助提升信息处理、方案推演和执行效率。

### 3.1 上下文组织

AI 协助快速读取和关联以下信息：

- 最近提交记录。
- 活动计划。
- 性能总结文档。
- 组件库 README。
- 架构文档。
- 关键代码文件职责。

提效价值：缩短进入复杂历史任务的时间，避免只基于局部代码做判断。

### 3.2 问题拆解

AI 协助将“高频行情卡顿”拆成多个可验证问题：

- 数据写入是否过于频繁。
- 是否存在不可见区域刷新。
- 是否由 per-cell ArkUI 组件结构带来额外开销。
- 响应式对象字段变更是否扩大刷新范围。
- 滚动和行情刷新是否竞争 UI 线程。
- Canvas draw 成本是否可控。

提效价值：把模糊性能问题转化为可分析、可验证的工程假设。

### 3.3 方案推演

AI 辅助梳理并比较多个阶段方案：

| 阶段 | 方案 | 结论 |
| --- | --- | --- |
| A | 逐 cell 写入 | 长帧明显，P95 曾达到 46ms、61ms、123ms 级别 |
| B | 调度合并 | 可减少写入次数，但不能根治组件结构问题 |
| C | 只刷新可见区域 | 有收益，但 per-cell 组件链路仍偏重 |
| D | Canvas 原型 | 路线成立，flush 成本明显下降 |
| D1 | 视口级 Canvas | 可进入推荐业务工作点，具备落地价值 |

提效价值：减少盲目重构，通过阶段化验证收敛技术路线。

### 3.4 跨文件实施

本次改造涉及组件、数据模型、Canvas 渲染、真实行情适配、示例页面、压测页面和文档。AI 辅助保持跨文件口径一致：

- 组件收敛为 Canvas-only。
- 高频数据模型去除响应式装饰。
- 普通行情刷新统一通过 `dataRevision` 触发。
- 最新价定位通过 `latestPriceAnchorRevision` 单独控制。
- 真实行情通过 `QuoteTableDeltaAdapter` 批量写入。
- README、架构文档、接入指南同步更新。

提效价值：降低跨文件遗漏和返工风险。

### 3.5 验证与沉淀

AI 辅助组织验证动作：

- 检查目标响应式装饰器是否移除。
- 检查 legacy 组件是否仍对外暴露。
- 检查压测页是否仍依赖旧组件模式。
- 执行完整构建验证。
- 检查文档是否与代码口径一致。

提效价值：让交付从“代码修改完成”升级为“可验证、可复用、可维护”。

## 4. 技术方案总结

本次优化最终采用视口级 Canvas 方案。

核心链路如下：

1. 服务端返回单元格增量行情。
2. 业务侧转换为 `QuoteTableCellDelta`。
3. `QuoteTableDeltaAdapter` 批量写入 `DataView`。
4. 普通行情刷新递增 `dataRevision`。
5. `TCanvasComponent` 请求重绘。
6. `TCanvasDataAdapter` 只读取可见区域附近数据。
7. `TCanvasRenderer` 完成 Canvas 绘制。

关键设计：

- `DataView` 是普通数据对象，不再依赖 `@Observed`。
- `TCanvasComponent` 通过普通对象引用读取 `DataView` 和 `GestureMonitor`。
- 高频行情赋值不再触发 ArkUI 对象字段响应式传播。
- 普通行情刷新与最新价定位解耦。
- 滚动中可暂停或节流 UI flush。
- Canvas 只绘制当前视口附近内容。

## 5. 实际完成内容

### 5.1 Canvas-only 收敛

`t_split_list` 当前只支持视口级 Canvas T 型报价实现。对外入口不再暴露 legacy `TComponent`、`TController`、`ScrollController`，压测页也不再保留旧组件模式切换。

### 5.2 高频链路去响应式

移除高频数据模型上的响应式装饰，降低行情直接赋值对 ArkUI 响应式传播链路的影响。Canvas 重绘改由显式版本号驱动。

### 5.3 显式刷新协议

建立两个版本号：

- `dataRevision`：普通行情刷新、批量 delta 写入后递增。
- `latestPriceAnchorRevision`：首次进入、合约切换、主动回到最新价时递增。

两者分离后，普通行情刷新不会反复把用户拉回最新价位置。

### 5.4 真实行情接入协议

通过 `QuoteTableDeltaAdapter` 支持服务端单格增量批量写入，业务层可以复用同一协议接入 mock、轮询、WebSocket 或真实推送。

### 5.5 业务能力补齐

本轮优化同时保留和完善了 T 型报价核心业务能力：

- 行权价排序。
- 最新价线居中。
- Call / Put 展开收起。
- 横纵手势方向锁。
- 惯性滑动。
- 单元格点击回调。
- 表头设置入口。
- 明暗主题。
- 颜色兜底。
- 缺失数据展示。

## 6. 性能收益

已有性能总结中记录的关键收益如下：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 平均 flush 成本 | 约 13-15ms | 约 1ms |
| Canvas draw 最大耗时 | 早期约 83ms | 视口级绘制后约 3.45ms |
| 推荐业务工作点 | 风险较高 | 20Hz + 部分变动 + 100ms flush + 只刷可见 + 滚动中暂停 flush |

说明：

- 组件表格逐 cell 更新在基准场景下存在明确长帧风险。
- Canvas 方案显著降低平均刷新成本。
- 视口级 Canvas 与 redraw 合并后，绘制尖刺明显下降。
- 20Hz 整表刷新属于压力边界，不建议作为默认业务策略。
